# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Jekyll static site for "The Candid Duo," a travel blog, deployed for free on GitHub Pages with a hand-built admin dashboard (`/admin`) as an on-site editor and Google AdSense monetization. There is no local build/run step required for normal edits — GitHub Pages builds the site automatically on push to `main`. Content is Markdown/YAML; the CMS commits directly to the repo via the GitHub REST API.

## Commands

No package.json/JS tooling — this is a plain Jekyll + Ruby site.

```bash
bundle install       # first time only, installs gems from Gemfile
bundle exec jekyll serve   # local preview at http://localhost:4000
```

There are no automated tests or linters in this repo. Verify changes by running `jekyll serve` and checking the page in a browser, or by inspecting the built `_site/` output.

## Architecture

**Content model (Jekyll collections/data driving the templates):**
- `_posts/` — blog posts (filename `YYYY-MM-DD-slug.md`). Front matter drives most layout logic: `category`, `destination` (must match one of Jeju/New Zealand/Tasmania/Umroh/Singapore/Other to link up with destination pages), `image`/`image_alt`, `dek`/`excerpt`, `tags`, `featured` (only one post should be `featured: true` — it becomes the homepage lead story).
- `_products/` — affiliate product recommendations (collection with `output: false` in `_config.yml`, so products have no individual pages — they only render as cards via `_includes/product-card.html` on the homepage and `/products/`). Front matter: `name`, `image`, `price`, `platform`, `country`, `category` (free text; also becomes a filter button on `/products/`, so reuse exact wording to group items), `affiliate_url` (the buy link behind every "Shop now" button/image/title), `blurb`, `featured`, `date`. **Never name a product field `url`**: on a collection item Jekyll's built-in `url` (its would-be page address, `/products/<slug>/`) always shadows a front matter key of the same name — no Liquid expression can read the raw value — so the buy buttons silently linked to non-existent internal pages until the field was renamed. `product-card.html` also prepends `https://` to a scheme-less link and drops the Shop now button (and link wrappers) when the link is blank or `#`.
- `_data/homepage.yml` — hero carousel slides, the scrolling ticker (WATCH/LISTEN/READ), and the "Watch & Listen" media cards. Fully editable via CMS.
- `_data/navigation.yml` — top nav menu items.
- `_data/socials.yml` — a `links:` list of `{platform, url}` driving the "Follow along" icon strip (`_includes/socials.html`), included at the end of `home.html` and, for the Contact page only, at the end of `_layouts/page.html` — both land directly above the footer (the footer used to open with a newsletter signup box; it was removed because it wasn't connected to a service — git history has the markup if one is added later). Editable in the CMS under Socials (a plain `datafile` section, like Navigation). The include renders nothing while the list is empty, prepends `https://` to a scheme-less URL and `mailto:` to an Email entry, and picks each icon by matching the lowercased `platform` name in a `{% case %}` — so a new platform needs an icon branch there as well as an option in `socialItemFields` (schema.js) — or, if it has no branch (Lemon8 doesn't), the `{% else %}` generic link icon is used. The Contact-page hook is keyed on `page.url == "/contact/"` rather than a front matter flag because the CMS's page editor drops front matter keys it doesn't know about on save. Note the footer's own small social icons still read `_config.yml`'s `social:` block, not this file.
- `destinations/*.md` — one page per destination (Jeju, New Zealand, Tasmania, Umroh), using `_layouts/category.html`, which pulls in `site.posts | where: "destination", page.destination`.
- Top-level pages (`about.md`, `contact.md`, `privacy.md`, `products.html`, `stories.html`) use `_layouts/page.html` or their own inline layout.

**Layouts (`_layouts/`) → Includes (`_includes/`) chain:**
- `default.html` is the base shell (head/header/footer) that everything else extends via `layout: default`.
- `home.html` (homepage) assembles hero, ticker, featured/latest stories, Watch & Listen, destinations grid, featured products, about teaser — all Liquid-driven from `site.posts`, `site.products`, and `site.data.homepage`.
- `post.html` renders an article, auto-inserts an in-article ad after the 3rd paragraph (if the article is long enough), shows prev/next nav, and a related-stories block filtered by same `destination` (falls back to any other posts if fewer than 3 matches). Also emits BlogPosting JSON-LD.
- `category.html` is the generic "posts filtered by destination" template used by `destinations/*.md`.
- Reusable pieces live in `_includes/`: `head.html` (fonts, CSS, SEO tag, conditional AdSense script loader, analytics), `header.html` (nav, reads `site.data.navigation.main`), `footer.html`, `hero.html`, `ticker.html`, `story-card.html`, `product-card.html`, `ad.html`.

**Ad slots (`_includes/ad.html`):** Ad units (`leaderboard`, `infeed`, `inarticle`) only render real AdSense `<ins>` markup when `site.adsense.enabled` is `true` AND `publisher_id` isn't the placeholder value; otherwise a visual placeholder is shown. When editing ad placement/behavior, this gating logic is the source of truth.

**Reading time:** Computed inline via Liquid (`content | number_of_words | divided_by: 200 | plus: 1`) wherever it's shown (post header, story cards, homepage lead), overridable per-post with a `read_time` front-matter field.

**Styling:** Single stylesheet `assets/css/main.css`. Design tokens (colors, fonts, spacing) are CSS custom properties in the `:root` block at the top — change the site's look by editing tokens there rather than hunting for hardcoded values.

**CMS — `admin/` (hand-built, not a third-party product):** A static single-page app, native ES modules, no build step, that reads/writes the repo's actual content files through the GitHub REST API — there's no server component beyond the OAuth worker below.
- `admin/js/schema.js` is the source of truth for what's editable: field definitions per content type (posts/products/homepage/navigation/pages), matching the front matter/`_data` schema described above. If you add/rename a front-matter field used in templates, update the matching entry here too, or the CMS form and the actual content shape will drift apart.
- `admin/js/content.js` hand-rolls front matter and `_data/*.yml` parsing/serialization (deliberately not a YAML library — the shapes here are fixed and simple). Serialization is schema-typed (`type: "date"` writes a bare/unquoted YAML timestamp, not a quoted string) because Jekyll's date sorting and filters need a real `Date`, not a string — this is easy to regress if a new date-like field is added without setting `type: "date"`.
- `admin/js/github-api.js` wraps the Contents API (get/put/delete, base64 encode/decode) and `admin/js/auth.js` implements the popup OAuth handshake — both talk to the same Cloudflare Worker Decap used to (`admin/js/config.js` holds `REPO`/`AUTH_BASE_URL`). Every save/delete sends the `sha` of the file as it was when the editor loaded; GitHub returns `409` (marked as `error.conflict = true`) if that no longer matches the file's current sha — meaning it changed elsewhere (another tab, another save, a direct GitHub edit) since this editor opened. Every editor's save/delete handler in `app.js` catches that specifically and offers a "Reload latest" button (via `showFormError(msg, action)`) that re-fetches the file fresh and reopens the same editor, rather than showing GitHub's raw error text and leaving the user stuck.
- `admin/js/app.js` is the renderer: sidebar, list/card views, and four editor patterns (`collection` = a folder of front-matter files like posts/products, `datafile` = tabbed repeating lists in one YAML file like homepage/navigation, `singles` = one fixed file per fixed page like about/contact/privacy, `settings` = one flat key-value file with no list/body — currently just `_data/settings.yml`'s `favicon`, via `renderSettingsEditor`/`content.js`'s `parseFlatYaml`/`serializeFlatYaml`). Two field types beyond the basics: `multiselect` (checkbox panel + removable chips, e.g. product `country`) and the hero-slide "populate from an existing story" picker (`renderDatafile`/`listItemHtml` in app.js) — a UI convenience that reads existing `_posts/` front matter to prefill a hero slide's image/title/subtitle/link; it doesn't change `_data/homepage.yml`'s shape. `loadPostSummaries()` prefers each post's wide `image_hero` crop over its raw `image` (see the `image_crop` notes below for why it isn't the 4:3 `image_thumb`).
- The favicon is the one setting that also affects `admin/index.html` itself — but that file has no front matter, so Jekyll copies it verbatim with zero Liquid processing. `applyFavicon()` in app.js works around this by reading `_data/settings.yml` at runtime (before login too — an anonymous read, like other public-repo reads in this CMS) and injecting a `<link rel="icon">` into `document.head` directly, rather than relying on any build-time templating. The live site's own favicon (`_includes/head.html`) reads the same field with a `| default:` fallback to the original static `/assets/images/favicon.svg`, so nothing breaks before the setting is ever saved.
- Collection list views (`renderCollectionList`) have a grid/list toggle (`getListView`/`setListView`, persisted per-collection in `localStorage`) — both views share the same date-descending sort and the `badgeInfo()` helper, which shows a DRAFT pill (from `schema.draftField`) ahead of FEATURED/category. Posts save-as-draft is just a `published: boolean` front-matter field (default `true`) — Jekyll's own `published: false` handling excludes it from `jekyll build` with zero custom logic needed; `loadPostSummaries()` (the hero-slide picker) filters drafts out since their URL wouldn't resolve live yet.
- The `image_crop` field type (`cropFor` pointing at the paired `image` field name) is a genuinely separate, physically-cropped file — not metadata on the original photo. A single source photo can have more than one crop for different display contexts, each its own `image_crop` field with its own `aspectW`/`aspectH` (crop frame shape) and `outputW`/`outputH` (exported file size) — posts have both `image_thumb` (4:3, 1200×900 — for story-card thumbnails, `listThumbnail: true` marks it as the one list/grid cards use via `findCropField`) and `image_hero` (16:9, 1600×900 — for the homepage hero banner). `fieldInputHtml`'s `"image"` case renders one small current-crop preview + "✂ {label}" button per paired crop field (`thumbCropRowHtml`, inside a shared `.crop-rows` wrapper); clicking one opens `openCropModal()` — a standard drag-to-pan + zoom-slider cropper — at that field's own aspect ratio and output size (passed in, not fixed constants, since different crops need different shapes). It always crops from a same-origin `blob:` URL (`toLocalBlobUrl()` fetches+blobs a `raw.githubusercontent.com` source first) since a cross-origin `<img>` would taint the `<canvas>` on export; the freshest local file (before its own upload even finishes) is preferred when available. Save uploads the cropped JPEG via the normal image pipeline into that specific paired field. `_includes/story-card.html` and `_layouts/home.html` (the lead/featured story, `.featured .card__media` — deliberately 4:3 to match `image_thumb` exactly, not a further crop) read `post.image_thumb | default: post.image`; the Homepage hero-slide "populate from a story" picker (`loadPostSummaries()`) reads `post.image_hero | default: post.image` instead — all additive, so posts saved before these fields existed still render their full original photo unchanged. The post-hero image (`_layouts/post.html`) intentionally always shows the uncropped original — it isn't a "thumbnail" context, and unlike the homepage hero it isn't full-bleed/panoramic either.
- Why two crops instead of one: the homepage hero (`.hero`, full-bleed, `height:clamp(580px,92vh,880px)`) is a far wider aspect ratio than a story-card thumbnail. Autofilling it from `image_thumb` was tried first and reproduced a real bug — `background-size:cover` re-crops the already-4:3-cropped image to fit the much wider hero box, shifting the subject and sometimes colliding it with the overlaid title text. `image_hero` exists so the admin composes the wide framing directly, once, rather than the site re-cropping a crop it wasn't intended for.
- Any markdown body field gets a "+ Insert image" toolbar (`bodyFieldHtml` + `wireBodyImageInsert()`) that uploads a photo and splices a `![]()` Markdown tag in at the textarea's cursor position — kramdown (Jekyll's default renderer) needs no template changes to display it.
- Beside it, "+ Insert video" (`wireBodyVideoInsert()`) opens a paste-a-link row and splices `{% include youtube.html id="…" %}` in at the saved cursor position. It exists because a bare YouTube URL in a body is **not** embedded — kramdown leaves it as plain text (no autolinking), so only the Liquid include (`_includes/youtube.html`, a responsive 16:9 `youtube-nocookie.com` iframe in `.video-embed`) produces a playable player. `parseYoutubeId()` in `admin/js/media.js` accepts watch/`youtu.be`/shorts/live/embed links (any of www/m./music. hosts) or a bare ID and returns only a strict 11-char `[\w-]` ID, so nothing user-typed can break out of the tag's quotes. YouTube only — Spotify/TikTok have no in-article equivalent (they exist only as Homepage → Watch & Listen cards).
- `admin/js/ai.js` + two UI panels in `app.js` are the CMS features with a real server component — `oauth-worker/worker.js` proxies both to the Gemini API (`callGemini()`, using `generationConfig.responseSchema` for structured output — note Gemini's schema uses uppercase type names like `"OBJECT"`/`"STRING"`, not standard JSON Schema) via a server-side `GEMINI_API_KEY` secret (never exposed to the browser, and free-tier — chosen specifically so this needs no billing setup). Both routes share a `requirePushAccess()` check that rejects any caller whose GitHub token doesn't have push access to `GITHUB_REPO` (another worker secret) — without that check, anyone who found the worker's URL could burn through the site owner's free-tier quota with a throwaway GitHub account.
  - The "✨ Generate with AI" panel (Stories → new entry only) calls `/generate-story` with a prompt plus optional images/PDF/text files, and fills the form fields from the structured (`responseSchema`) result.
  - The "Fetch details" panel (Products, new or existing) calls `/fetch-product` with a pasted affiliate URL. The worker fetches the page server-side (the browser can't, due to CORS), asks Gemini to extract name/price/blurb/category/image from the raw HTML, and best-effort downloads the image too so it gets uploaded to `UPLOADS_PATH` like any other CMS image instead of hot-linking someone else's CDN URL — if that download fails, it falls back to the bare external image URL, which `imageSrc()`/Jekyll's `relative_url` both already pass through unchanged. Bot-blocking storefronts (Amazon, notably) commonly return little or nothing; the UI surfaces that as a "fill in what's missing" status rather than failing silently.
- `admin/js/media.js` + two buttons on Homepage → Watch & Listen (`mediaFetchActionsHtml`/`wireMediaFetchActions` in app.js) populate a `media_features` item with a real, playable embed instead of a hand-typed thumbnail+link card. Both worker routes are intentionally *not* behind `requirePushAccess` — they're free public lookups with no quota to protect, so they work even without the Gemini/GITHUB_REPO secrets configured (only the worker code itself needs to be current).
  - **YouTube** (`/latest-youtube`) resolves the channel URL in `admin/js/config.js`'s `YOUTUBE_CHANNEL_URL` to a channel ID (tries the page's canonical `<link>` tag first, then two JSON-key fallbacks — YouTube has changed the embedded field name before) and reads the channel's free public Atom feed for the newest `<entry>`. That feed 404s for a channel with zero uploads rather than returning an empty feed — worth knowing if this ever seems "broken" on a fresh channel.
  - **TikTok** (`/tiktok-oembed`) has no equivalent discovery mechanism (would need TikTok's developer API + approval), so the admin pastes one video URL and the route resolves it via TikTok's public oEmbed endpoint, rejecting profile links (`embed_type !== "video"`). Its `thumbnail_url` is a signed, expiring CDN link (has an `x-expires` param) — the CMS deliberately does not persist it into `image`, since the real embed shows its own live preview once `embed.js` runs.
  - Both write an `embed_id` onto the `media_features` item (`mediaItemFields` in schema.js). `_layouts/home.html`'s Watch & Listen loop branches on `platform` + `embed_id`: YouTube renders inside `.media-embed--youtube` (a fixed 4:3 box the iframe letterboxes into), TikTok renders inside `.media-embed--tiktok` (no forced aspect-ratio — TikTok's embed is portrait-native and sizes itself, so those cards end up taller than their siblings; that's expected, not a bug) plus a page-wide `<script src="tiktok.com/embed.js">` added once if any item needs it. Items without an `embed_id` (Spotify, or anything added by hand) keep the original thumbnail+link-out card.
- This is infrastructure the user deploys separately to Cloudflare, not part of the Jekyll build.

**`_config.yml`:** Central site settings — `url`/`baseurl` (must match the GitHub Pages URL), `adsense` block (enable/publisher ID/slot IDs), `social` links, `google_analytics`, and `exclude` (keeps docs/tooling files out of the Jekyll build).
