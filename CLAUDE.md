# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Jekyll static site for "The Candid Duo," a travel blog, deployed for free on GitHub Pages with a hand-built admin dashboard (`/admin`) as an on-site editor and Google AdSense monetization. There is no local build/run step required for normal edits — GitHub Pages builds the site automatically on push to `main`. Content is Markdown/YAML; the CMS commits directly to the repo via the GitHub REST API.

## Commands

No package.json/JS tooling for the site itself — it's a plain Jekyll + Ruby site. The one exception is `admin/editor-src/` (see the visual-editor note under the CMS section): a small npm project that *builds* the CMS's rich-text editor into a committed file, `admin/lib/editor.bundle.js`. Nothing in normal editing, `jekyll serve`, or GitHub Pages runs it; you only need Node if you're changing the editor engine itself.

```bash
bundle install       # first time only, installs gems from Gemfile
bundle exec jekyll serve   # local preview at http://localhost:4000
```

There is no linter and no test suite for the Jekyll site itself — verify changes by running `jekyll serve` and checking the page in a browser, or by inspecting the built `_site/` output. The only automated tests are for the two JS subsystems: the visual editor (`cd admin/editor-src && npm test`, plus the kramdown comparison described under the CMS section) and the worker's traffic counter (`node --test oauth-worker/test/stats.test.mjs oauth-worker/test/tracker.test.mjs`, Node 22+, no dependencies).

## Architecture

**Content model (Jekyll collections/data driving the templates):**
- `_posts/` — blog posts (filename `YYYY-MM-DD-slug.md`). Front matter drives most layout logic: `section` (the blog's two niches — a list, `["Travel"]`, `["Family"]` or both for a trip with the kids; a post with no `section` is treated as Travel everywhere), `category` (the *kind* of story — Culture/Adventure/Guide/Food/Reflection/Parenting/Kids' Activities/Milestones — independent of section), `destination` (optional — blank for at-home family posts; otherwise must match one of Jeju/New Zealand/Tasmania/Umroh/Singapore/Other to link up with destination pages), `image`/`image_alt`, `dek`/`excerpt`, `tags`, `featured` (only one post should be `featured: true` — it becomes the homepage lead story). Filter on section with `where: "section", "Family"` — Jekyll's `where` matches inside a list, and also a plain `section: Family` string. GitHub Pages' Jekyll 3.10 can't express "no section *or* Travel" in a filter, which is why every post carries an explicit section.
- `_products/` — affiliate product recommendations (collection with `output: false` in `_config.yml`, so products have no individual pages — they only render as cards via `_includes/product-card.html` on the homepage and `/products/`). Front matter: `name`, `image`, `price`, `platform`, `country`, `category` (free text; also becomes a filter button on `/products/`, so reuse exact wording to group items), `affiliate_url` (the buy link behind every "Shop now" button/image/title), `blurb`, `featured`, `date`. **Never name a product field `url`**: on a collection item Jekyll's built-in `url` (its would-be page address, `/products/<slug>/`) always shadows a front matter key of the same name — no Liquid expression can read the raw value — so the buy buttons silently linked to non-existent internal pages until the field was renamed. `product-card.html` also prepends `https://` to a scheme-less link and drops the Shop now button (and link wrappers) when the link is blank or `#`.
- `_digital_products/` — **our own** digital products (currently the "30 Days of Montessori Play" printables on Gumroad), a separate collection from the affiliate `_products/` (also `output: false`). Front matter: `name`, `image`, `format` (small label above the name, e.g. "Printable PDF · 24 pages"), `price`, optional `price_was` (shown crossed out), `gumroad_url` and `etsy_url` (either or both — one button per store; the image and title link to the Gumroad one if set, else Etsy; never a field called `url`, same Jekyll shadowing problem as `affiliate_url`), `blurb`, optional `order` (number; lowest first, products without one follow newest-first), `featured`, `date`. Rendered by `_includes/digital-products.html` (ordering + grid, optional `limit`/`featured_first`/`store_links`) and `_includes/digital-card.html` (same look as `product-card.html`, but plain `rel="noopener"` — no `sponsored`/`nofollow` — and no affiliate disclosure, since these are ours). Shown on the homepage ("From Our Shop", 3 cards, featured first, above "Our Recent Fav Products") and at the top of `/products/` ("Made by Us"), which then becomes a two-part Shop page; both hide themselves while the collection is empty. The "Visit our Gumroad store" / "Visit our Etsy shop" buttons are built from any `Gumroad`/`Etsy` entries in `_data/socials.yml`, so the store address lives in one place (CMS → Socials). CMS: the "Digital Products" section (`digitalFields` in schema.js; `order` uses the `number` field type).
- `_data/homepage.yml` — hero carousel slides, the scrolling ticker (WATCH/LISTEN/READ), and the "Watch & Listen" media cards. Fully editable via CMS.
- `_data/navigation.yml` — top nav menu items.
- `_data/socials.yml` — a `links:` list of `{platform, url}` driving the "Follow along" icon strip (`_includes/socials.html`), included at the end of `home.html` and, for the Contact page only, at the end of `_layouts/page.html` — both land directly above the footer (the footer used to open with a newsletter signup box; it was removed because it wasn't connected to a service — git history has the markup if one is added later). Editable in the CMS under Socials (a plain `datafile` section, like Navigation). The include renders nothing while the list is empty, prepends `https://` to a scheme-less URL and `mailto:` to an Email entry, and picks each icon by matching the lowercased `platform` name in a `{% case %}` — so a new platform needs an icon branch there as well as an option in `socialItemFields` (schema.js) — or, if it has no branch (Lemon8 doesn't), the `{% else %}` generic link icon is used. The Contact-page hook is keyed on `page.url == "/contact/"` rather than a front matter flag because the CMS's page editor drops front matter keys it doesn't know about on save. Note the footer's own small social icons still read `_config.yml`'s `social:` block, not this file. Gumroad and Etsy share a shopping-bag icon branch. (A Gumroad link was once saved under the Email platform, which rendered as `mailto:https://…` — use the Gumroad platform for it.)
- `destinations/*.md` — one page per destination (Jeju, New Zealand, Tasmania, Umroh), using `_layouts/category.html`, which lists `site.posts | where: page.filter_by, <that field's value on the page>` — `filter_by` defaults to `destination`, so a destination page only sets `destination:`. `family.md` (`/family/`, the Family hub) reuses the same layout with `filter_by: section` + `section: Family`, plus the optional `eyebrow`, `filters: true` (category buttons, shown once 2+ categories exist), `empty` and `back_url`/`back_text` keys documented at the top of the layout.
- **Family niche (added 2026-10, launching in phases):** launched 2026-10-02 with the first Family post; `/family/` is linked from the nav (`_data/navigation.yml`) and the footer's Explore column. The homepage "Family Life" row (`home.html`, 3 newest Family posts, above Destinations) and the Travel/Family buttons on `/stories/` only render when `where: "section", "Family"` is non-empty, so they'd hide again if every Family post were unpublished. Still to do: the travel-only copy (`_config.yml` tagline/description, `index.html` title/description, `about.md`, `contact.md`, `stories.html`/`products.html` leads, the homepage About teaser and products lead line).
- **Destination cards** (homepage "Destinations" section and the `/destinations/` page) are one shared include, `_includes/destination-cards.html`: compact strip cards (~100px tall) with the country's flag, the place name and story count over a dimmed photo (`.dest-grid--compact` / `.dest-card--flag` in main.css; the taller `.dest-card` rules underneath are the base they override, and are no longer used on their own). The include builds the cards from parallel Liquid arrays (`dests`, `dimgs`, `dflags`, `dcountries`) — **adding a destination means adding an entry to each array**, plus a photo in `assets/images/` and a flag SVG. Flags live in `assets/images/flags/<iso-code>.svg` (4:3 artwork from the MIT-licensed `flag-icons` package; its license text is in that folder — keep it if you add flags; flags for other countries are in that project's `flags/4x3/` folder at github.com/lipis/flag-icons). The mapping is by *country*, not destination name: Jeju → `kr`, Tasmania → `au`, Umroh → `sa` (Mecca). The flag `<img>` sits inside `.dest-card`, so `.dest-card .dest-card__flag` deliberately overrides the photo rules (`.dest-card img`: fill the card, dim, hover-zoom).
- Top-level pages (`about.md`, `contact.md`, `privacy.md`, `products.html`, `stories.html`) use `_layouts/page.html` or their own inline layout.

**Layouts (`_layouts/`) → Includes (`_includes/`) chain:**
- `default.html` is the base shell (head/header/footer) that everything else extends via `layout: default`.
- `home.html` (homepage) assembles hero, ticker, featured/latest stories, Watch & Listen, destinations grid, featured products, about teaser — all Liquid-driven from `site.posts`, `site.products`, and `site.data.homepage`.
- `post.html` renders an article, auto-inserts an in-article ad after the 3rd paragraph (if the article is long enough), and ends with a "Keep Reading" block of up to 3 related stories: same `destination` first (only if the post has one — a nil destination would otherwise "match" every other destination-less post), then the same section (a post in both counts as Family), then anything else, de-duplicated via a `|url|url|` string. There is deliberately no separate previous/next pager — it duplicated that block. Also emits BlogPosting JSON-LD.
- `category.html` is the generic "posts filtered by destination" template used by `destinations/*.md`.
- Reusable pieces live in `_includes/`: `head.html` (fonts, CSS, SEO tag, conditional AdSense script loader, analytics), `header.html` (nav, reads `site.data.navigation.main`), `footer.html`, `hero.html`, `ticker.html`, `story-card.html`, `product-card.html`, `ad.html`.

**Ad slots (`_includes/ad.html`):** Ad units (`leaderboard`, `infeed`, `inarticle`) only render real AdSense `<ins>` markup when `site.adsense.enabled` is `true` AND `publisher_id` isn't the placeholder value; otherwise a visual placeholder is shown. When editing ad placement/behavior, this gating logic is the source of truth.

**Reading time:** Computed inline via Liquid (`content | number_of_words | divided_by: 200 | plus: 1`) wherever it's shown (post header, story cards, homepage lead), overridable per-post with a `read_time` front-matter field.

**Styling:** Single stylesheet `assets/css/main.css`. Design tokens (colors, fonts, spacing) are CSS custom properties in the `:root` block at the top — change the site's look by editing tokens there rather than hunting for hardcoded values. Every page title (`.page-hero`) and story title (`.post-hero`) sits on a full-width `--bg-alt` band, painted edge to edge with a `box-shadow` + `clip-path` trick so the markup stays a plain `.wrap` and new pages get the band for free. Only the homepage floats its header over the content; everywhere else the header is sticky (in the flow), so those heroes' top padding is just the gap under it. Two untinted `.section`s in a row get a hairline instead of double padding (`.section:not(.section--alt) + .section:not(.section--alt)`).

**CMS — `admin/` (hand-built, not a third-party product):** A static single-page app, native ES modules, no build step for the app itself, that reads/writes the repo's actual content files through the GitHub REST API — there's no server component beyond the OAuth worker below.
- `admin/js/schema.js` is the source of truth for what's editable: field definitions per content type (posts/products/homepage/navigation/pages), matching the front matter/`_data` schema described above. If you add/rename a front-matter field used in templates, update the matching entry here too, or the CMS form and the actual content shape will drift apart.
- `admin/js/content.js` hand-rolls front matter and `_data/*.yml` parsing/serialization (deliberately not a YAML library — the shapes here are fixed and simple). Serialization is schema-typed (`type: "date"` writes a bare/unquoted YAML timestamp, not a quoted string) because Jekyll's date sorting and filters need a real `Date`, not a string — this is easy to regress if a new date-like field is added without setting `type: "date"`.
- `admin/js/github-api.js` wraps the Contents API (get/put/delete, base64 encode/decode) and `admin/js/auth.js` implements the popup OAuth handshake — both talk to the same Cloudflare Worker Decap used to (`admin/js/config.js` holds `REPO`/`AUTH_BASE_URL`). Every save/delete sends the `sha` of the file as it was when the editor loaded; GitHub returns `409` (marked as `error.conflict = true`) if that no longer matches the file's current sha — meaning it changed elsewhere (another tab, another save, a direct GitHub edit) since this editor opened. Every editor's save/delete handler in `app.js` catches that specifically and offers a "Reload latest" button (via `showFormError(msg, action)`) that re-fetches the file fresh and reopens the same editor, rather than showing GitHub's raw error text and leaving the user stuck.
- `admin/js/app.js` is the renderer: sidebar, list/card views, and four editor patterns (`collection` = a folder of front-matter files like posts/products, `datafile` = tabbed repeating lists in one YAML file like homepage/navigation, `singles` = one fixed file per fixed page like about/contact/privacy, `settings` = one flat key-value file with no list/body — currently just `_data/settings.yml`'s `favicon`, via `renderSettingsEditor`/`content.js`'s `parseFlatYaml`/`serializeFlatYaml`). Two field types beyond the basics: `multiselect` (checkbox panel + removable chips, e.g. product `country` and post `section`) and the hero-slide "populate from an existing story" picker (`renderDatafile`/`listItemHtml` in app.js) — a UI convenience that reads existing `_posts/` front matter to prefill a hero slide's image/title/subtitle/link; it doesn't change `_data/homepage.yml`'s shape. A `select` always submits one of its options unless it has `emptyOption: "<label>"` (post `destination` does), which adds a blank first choice that saves as no value — otherwise a new at-home post would silently get the first destination. `loadPostSummaries()` prefers each post's wide `image_hero` crop over its raw `image` (see the `image_crop` notes below for why it isn't the 4:3 `image_thumb`).
- The favicon is the one setting that also affects `admin/index.html` itself — but that file has no front matter, so Jekyll copies it verbatim with zero Liquid processing. `applyFavicon()` in app.js works around this by reading `_data/settings.yml` at runtime (before login too — an anonymous read, like other public-repo reads in this CMS) and injecting a `<link rel="icon">` into `document.head` directly, rather than relying on any build-time templating. The live site's own favicon (`_includes/head.html`) reads the same field with a `| default:` fallback to the original static `/assets/images/favicon.svg`, so nothing breaks before the setting is ever saved.
- Collection list views (`renderCollectionList`) have a grid/list toggle (`getListView`/`setListView`, persisted per-collection in `localStorage`) — both views share the same date-descending sort and the `badgeInfo()` helper, which shows a DRAFT pill (from `schema.draftField`) ahead of FEATURED/category. Posts save-as-draft is just a `published: boolean` front-matter field (default `true`) — Jekyll's own `published: false` handling excludes it from `jekyll build` with zero custom logic needed; `loadPostSummaries()` (the hero-slide picker) filters drafts out since their URL wouldn't resolve live yet.
- The `image_crop` field type (`cropFor` pointing at the paired `image` field name) is a genuinely separate, physically-cropped file — not metadata on the original photo. A single source photo can have more than one crop for different display contexts, each its own `image_crop` field with its own `aspectW`/`aspectH` (crop frame shape) and `outputW`/`outputH` (exported file size) — posts have both `image_thumb` (4:3, 1200×900 — for story-card thumbnails, `listThumbnail: true` marks it as the one list/grid cards use via `findCropField`) and `image_hero` (16:9, 1600×900 — for the homepage hero banner). `fieldInputHtml`'s `"image"` case renders one small current-crop preview + "✂ {label}" button per paired crop field (`thumbCropRowHtml`, inside a shared `.crop-rows` wrapper); clicking one opens `openCropModal()` — a standard drag-to-pan + zoom-slider cropper — at that field's own aspect ratio and output size (passed in, not fixed constants, since different crops need different shapes). It always crops from a same-origin `blob:` URL (`toLocalBlobUrl()` fetches+blobs a `raw.githubusercontent.com` source first) since a cross-origin `<img>` would taint the `<canvas>` on export; the freshest local file (before its own upload even finishes) is preferred when available. Save uploads the cropped JPEG via the normal image pipeline into that specific paired field. `_includes/story-card.html` and `_layouts/home.html` (the lead/featured story, `.featured .card__media` — deliberately 4:3 to match `image_thumb` exactly, not a further crop) read `post.image_thumb | default: post.image`; the Homepage hero-slide "populate from a story" picker (`loadPostSummaries()`) reads `post.image_hero | default: post.image` instead — all additive, so posts saved before these fields existed still render their full original photo unchanged. The post-hero image (`_layouts/post.html`) intentionally always shows the uncropped original — it isn't a "thumbnail" context, and unlike the homepage hero it isn't full-bleed/panoramic either.
- Why two crops instead of one: the homepage hero (`.hero`, full-bleed, `height:clamp(580px,92vh,880px)`) is a far wider aspect ratio than a story-card thumbnail. Autofilling it from `image_thumb` was tried first and reproduced a real bug — `background-size:cover` re-crops the already-4:3-cropped image to fit the much wider hero box, shifting the subject and sometimes colliding it with the overlaid title text. `image_hero` exists so the admin composes the wide framing directly, once, rather than the site re-cropping a crop it wasn't intended for.
- **Uploaded photos are shrunk in the browser first** (`admin/js/image-shrink.js`, called from `uploadImage()` in app.js): JPEG/HEIC are rotated upright per EXIF, scaled to ≤2000px on the long edge and re-encoded as JPEG at 0.8, which also strips metadata (phone photos carry GPS coordinates). PNG/GIF upload unchanged. Uploads made before this existed were shrunk once with the same numbers (in place, same filenames), so keep `MAX_EDGE`/`JPEG_QUALITY` in step if you change them.
- Any markdown body field gets a "+ Insert image" toolbar (`bodyFieldHtml` + `wireBodyImageInsert()`) that uploads a photo and splices a `![]()` Markdown tag in at the textarea's cursor position — kramdown (Jekyll's default renderer) needs no template changes to display it.
- Beside it, "+ Insert video" (`wireBodyVideoInsert()`) opens a paste-a-link row and splices `{% include youtube.html id="…" %}` in at the saved cursor position. It exists because a bare YouTube URL in a body is **not** embedded — kramdown leaves it as plain text (no autolinking), so only the Liquid include (`_includes/youtube.html`, a responsive 16:9 `youtube-nocookie.com` iframe in `.video-embed`) produces a playable player. `parseYoutubeId()` in `admin/js/media.js` accepts watch/`youtu.be`/shorts/live/embed links (any of www/m./music. hosts) or a bare ID and returns only a strict 11-char `[\w-]` ID, so nothing user-typed can break out of the tag's quotes. YouTube only — Spotify/TikTok have no in-article equivalent (they exist only as Homepage → Watch & Listen cards).
- **Admin theme** (`admin/style.css`): a light theme — white/off-white surfaces with the brand terracotta as the highlight and a soft warm tan as the second colour. Every colour lives in the `:root` tokens at the top (no colours are hard-coded in `app.js`/`richtext.js`/`index.html`, so re-theming is a one-block change): `--bg` off-white page, `--panel` white, `--panel-alt`/`--tan` tan tints, `--accent` terracotta fill (nudged ~1% darker than the site's `#c05a2f` so white button text meets WCAG AA), `--accent-text` for *small* terracotta text (plain `--accent` is 4.1:1 on the page — too faint for eyebrows/links), `--accent-soft` for active/selected washes. Keep new colour pairs ≥4.5:1 (≥3:1 for placeholders/large text). The visual editor's writing surface is deliberately plain white with the live article's type; its video card stays dark on purpose.
- **Dashboard** (`admin/js/dashboard.js`, first menu item and the page the CMS opens on): a `kind: "dashboard"` entry in `SCHEMA` (no content file behind it) — `renderSection` dispatches it to `renderDashboard()`. Four cards, each loading independently with its own loading / error / retry state (one slow or failed piece never blanks the page): **Traffic** (below), **Site status** (`GH.getLatestPagesBuild` → Live / Publishing… — it re-polls every 10s while a build runs — / "didn't finish", explaining that GitHub *cancels* earlier builds when saves land in quick succession: those show `errored` with a 0s duration and are harmless), **Content** (live/draft/scheduled story counts, days since last story, words, products *without a buy link*, a warning when more than one story is `featured` — only the newest shows), and **Recent activity** (recent commits, hiding the noisy "Upload image" ones). Posts/products are read the same N+1 way as the list pages and shared between cards. `openNewItem()` in app.js jumps from "+ New story" straight into the editor *without* rendering the list first (the list loads async and would overwrite the editor). Test the UI with fetch stubs — GitHub's anonymous API allows only 60 reads/hour, which ad-hoc testing exhausts quickly.
- **Traffic counter** — the Dashboard's numbers come from a small, cookie-free, first-party counter, *not* GitHub (repo "traffic" API only counts views of the repo page on github.com, never the Pages site) and not Google Analytics (its numbers can't be read into the CMS without a Google OAuth project). Three pieces: (1) the tiny inline script in `_includes/analytics.html` (on every public page via `head.html`, switched by `stats_url` in `_config.yml`) `sendBeacon`s `{p: path, r: referrer-host}` as `text/plain` (a "simple" request: no CORS preflight) to the worker's `/hit`; it does nothing off the real host, with Do Not Track, in automated browsers, or when `localStorage.cd_ignore` is set. (2) `oauth-worker/worker.js` — `/hit` (public, always answers 204, counts in `ctx.waitUntil`, ignores bots and any request whose `Origin` isn't the site) writes to a **D1** database bound as `DB` (tables are created lazily, so the owner only creates + binds the DB; `withStatsTables` self-heals if the DB is swapped); `/stats?days=N` (needs a GitHub session with push access via `requirePushAccess(request, env, { ai: false })` — the Gemini key is *not* required for it) returns totals, a zero-filled daily series, the previous period, and top pages/referrers/countries/devices. Days roll over at midnight **Singapore** time (`STATS_TZ_OFFSET_MIN`). Privacy design: no IP or user agent is ever stored; "unique visitors" = a per-day count of one-way hashes of IP+UA+a random daily salt, and the `seen`/`salts` rows are purged after ~1 day (only the per-day *counts* persist) — `privacy.md`'s Analytics section describes exactly this, so keep them in step. (3) `admin/js/stats.js` + the traffic card. `fetchStats()` never throws: it returns a state (`ok`, `needs_worker_update`, `needs_database`, `missing_secret`, `unauthorized`, `offline`, `error`) that the card turns into the right next-step message (`setupCard()`). **Gotcha:** an old worker has no `/stats` route, so its bare 404 carries no CORS headers and the browser reports it as a *failed request*, indistinguishable from being offline — so on a fetch failure `fetchStats` probes the worker's health page with a `no-cors` request: reachable ⇒ `needs_worker_update`, unreachable ⇒ `offline`. The CMS marks the owner's own browser with `cd_ignore` on login (`keepOwnerOutOfStats()` in app.js; the Dashboard's "Count my visits" toggles `cd_count_me` to opt back in) so testing the site doesn't inflate a small blog's numbers — which also means a normal-browser test visit won't show up; use a private window. Setup steps for the owner are SETUP-GUIDE Step 6g. Ideas not built yet: outbound "Shop now" click counting via the same beacon, Search Console / AdSense revenue (need Google OAuth).
- **Visual (rich text) story editor.** The Story body opens in a WYSIWYG editor (TipTap/ProseMirror) with a Visual | Markdown switch (last choice remembered in `localStorage` as `cms.bodyMode`); other body fields — Pages, Products — stay plain Markdown boxes, opted in per field with `richText: true` in `schema.js` (never Pages: `contact.md` holds a raw `<form>` and `<script>` a visual editor would destroy). Pieces: `admin/js/richtext.js` (toolbar, mode switch, link / photo-description rows; loads the bundle lazily with `import()` so only story editors pay for it) and the engine in `admin/editor-src/src/` → built to `admin/lib/editor.bundle.js` (+ `THIRD-PARTY-LICENSES.txt`, regenerated by the same build). Rebuild after editing anything in `editor-src/src/`: `cd admin/editor-src && npm install && npm run build`. (The output folder is deliberately `lib/`, not `vendor/` — `.gitignore` and `_config.yml` both treat `vendor` specially. `_config.yml` excludes `admin/editor-src` so only the built bundle ships.)
  - **The body `<textarea>` stays the single source of truth.** Save, drafts, the AI generator and "+ Insert image/video" all still read/write it. The visual editor mirrors *into* it only on a real user edit (`onChange`), never on load — opening and saving a story never rewrites its Markdown. `setFieldValue()` fires a `cms:external-set` event so an AI-generated body reaches the visual editor too. The insert buttons ask `bodyAdapters` whether the visual editor is showing and insert into it if so, else splice Markdown as before.
  - **Round-trip safety is the whole risk of a rich editor**, so: (1) `preprocess.js` lifts block-level Liquid tags and HTML comments out into opaque `RawBlock` nodes written back byte-for-byte (they render as a video card / a dashed "hidden note" / a template-tag chip); (2) `analyzeMarkdown()` detects anything else the editor can't hold (raw HTML, inline Liquid, kramdown `{: }` attributes, footnotes) and the story then opens — and stays — in Markdown mode with an explanation; (3) `soft-break.js` works around a tiptap-markdown bug that glued words together across a hard-wrapped line break after bold/italic/links. Note the site renders with **kramdown**, not CommonMark: e.g. `##Heading` with no space is a plain paragraph in kramdown (so on the live site too), and the editor shows it the same way.
  - **Tests** (`cd admin/editor-src && npm test`): loads every `_posts/*.md` body plus `test/fixtures-kitchen-sink.md` into the editor, serializes it back, and checks the rendered HTML is identical, that raw blocks survive verbatim, and that `analyzeMarkdown()` flags what it must. `test/kramdown-compare.rb` repeats the comparison with the real kramdown GFM renderer (`RT_DUMP_DIR=/tmp/rt npm test && bundle exec ruby test/kramdown-compare.rb /tmp/rt`) — that is the authoritative check; the JS one is a fast proxy. Re-run both after upgrading TipTap/tiptap-markdown or touching `preprocess.js`.
- `admin/js/ai.js` + two UI panels in `app.js` are the CMS features with a real server component — `oauth-worker/worker.js` proxies both to the Gemini API (`callGemini()`, using `generationConfig.responseSchema` for structured output — note Gemini's schema uses uppercase type names like `"OBJECT"`/`"STRING"`, not standard JSON Schema) via a server-side `GEMINI_API_KEY` secret (never exposed to the browser, and free-tier — chosen specifically so this needs no billing setup). Both routes share a `requirePushAccess()` check that rejects any caller whose GitHub token doesn't have push access to `GITHUB_REPO` (another worker secret) — without that check, anyone who found the worker's URL could burn through the site owner's free-tier quota with a throwaway GitHub account.
  - The "✨ Generate with AI" panel (Stories → new entry only) calls `/generate-story` with a prompt plus optional images/PDF/text files, and fills the form fields from the structured (`responseSchema`) result — including `section` and `category`, which the CMS only applies if they're among the field's options in schema.js (so an older worker, or a value Gemini invents, is simply ignored). The allowed values are spelled out in the schema *descriptions* (`SECTION_LIST`/`CATEGORY_LIST` in worker.js), not as a Gemini `enum`, so a schema-format quirk can't break generation; keep those lists in step with schema.js.
  - The "Fetch details" panel (Products, new or existing) calls `/fetch-product` with a pasted affiliate URL. The worker fetches the page server-side (the browser can't, due to CORS), asks Gemini to extract name/price/blurb/category/image from the raw HTML, and best-effort downloads the image too so it gets uploaded to `UPLOADS_PATH` like any other CMS image instead of hot-linking someone else's CDN URL — if that download fails, it falls back to the bare external image URL, which `imageSrc()`/Jekyll's `relative_url` both already pass through unchanged. Bot-blocking storefronts (Amazon, notably) commonly return little or nothing; the UI surfaces that as a "fill in what's missing" status rather than failing silently.
- `admin/js/media.js` + two buttons on Homepage → Watch & Listen (`mediaFetchActionsHtml`/`wireMediaFetchActions` in app.js) populate a `media_features` item with a real, playable embed instead of a hand-typed thumbnail+link card. Both worker routes are intentionally *not* behind `requirePushAccess` — they're free public lookups with no quota to protect, so they work even without the Gemini/GITHUB_REPO secrets configured (only the worker code itself needs to be current).
  - **YouTube** (`/latest-youtube`) resolves the channel URL in `admin/js/config.js`'s `YOUTUBE_CHANNEL_URL` to a channel ID (tries the page's canonical `<link>` tag first, then two JSON-key fallbacks — YouTube has changed the embedded field name before) and reads the channel's free public Atom feed for the newest `<entry>`. That feed 404s for a channel with zero uploads rather than returning an empty feed — worth knowing if this ever seems "broken" on a fresh channel.
  - **TikTok** (`/tiktok-oembed`) has no equivalent discovery mechanism (would need TikTok's developer API + approval), so the admin pastes one video URL and the route resolves it via TikTok's public oEmbed endpoint, rejecting profile links (`embed_type !== "video"`). Its `thumbnail_url` is a signed, expiring CDN link (has an `x-expires` param) — the CMS deliberately does not persist it into `image`, since the real embed shows its own live preview once `embed.js` runs.
  - Both write an `embed_id` onto the `media_features` item (`mediaItemFields` in schema.js). `_layouts/home.html`'s Watch & Listen loop branches on `platform` + `embed_id`: YouTube renders inside `.media-embed--youtube` (a fixed 4:3 box the iframe letterboxes into), TikTok renders inside `.media-embed--tiktok` (no forced aspect-ratio — TikTok's embed is portrait-native and sizes itself, so those cards end up taller than their siblings; that's expected, not a bug) plus a page-wide `<script src="tiktok.com/embed.js">` added once if any item needs it. Items without an `embed_id` (Spotify, or anything added by hand) keep the original thumbnail+link-out card.
- This is infrastructure the user deploys separately to Cloudflare, not part of the Jekyll build.

**Custom domain:** the site lives at `https://thecandidduo.com` (bought 2026-10 on Cloudflare Registrar, DNS on Cloudflare — the GitHub records must stay "DNS only", grey cloud, or GitHub can't issue its HTTPS certificate). The repo-root `CNAME` file is what points GitHub Pages at it (branch publishing reads it; deleting it reverts the site to github.io), and `thecandidduo.github.io` 301-redirects there. The repo itself is still named `thecandidduo/thecandidduo.github.io` — `REPO` in `admin/js/config.js` and the worker's `GITHUB_REPO` secret keep that name; only addresses of the *site* changed (`_config.yml` `url`, `admin/js/config.js` `SITE_URL`, the worker's `DEFAULT_SITE_ORIGINS`). The page-view counter only counts hits whose `Origin` is on that worker list, so a future domain change must update it (and the owner must redeploy the worker) or the Dashboard goes quiet.

**`_config.yml`:** Central site settings — `url`/`baseurl` (must match the live site address — the custom domain above), `adsense` block (enable/publisher ID/slot IDs), `social` links, `google_analytics`, `stats_url` (the worker address the page-view counter reports to; `""` switches counting off), and `exclude` (keeps docs/tooling files out of the Jekyll build).
